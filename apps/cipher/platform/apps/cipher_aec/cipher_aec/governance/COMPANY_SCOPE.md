# Explicit Company scope

Company-only business records use the native Company aggregate and need no Project. A duty, receipt or history record declares `scope_type = Company` and a null Project. Project scope declares `scope_type = Project` and a real Project belonging to the exact Company. Canonical Company and Project duties are independent. A null Project never expands authority to every Project.

`context.company_duty_rows(actor, company=None, lock=False)` selects only Company scope and an empty/null Project. `require_company(company, ability='company.read', actor=None, lock=False)` refreshes canonical identity, requires company.read plus the requested Company duty, checks native Company read permission, and optionally locks current rows. The initial abilities are company.read, commercial.read and commercial.write. Native Company query/record hooks enforce Company membership. Session company choices include Company-only actors, and `company_scopes` reports their exact Company capabilities separately from aggregate Project capabilities.

`commands.run_company_command(*, company, operation_id, command, payload, ability, effect, guard=None, participant_people=())` shares the canonical-person UUID receipt engine with Project commands. Callback signatures are `(actor, locked_company)`. Participating Person rows are sorted and locked before identity/User and Company rows. Company request hashes explicitly bind Company scope and null Project. Existing Project request-hash bodies remain unchanged. Cross-scope reuse of a person's UUID conflicts; aliases share the same namespace. Receipt lookup and current source rights precede new-effect lifecycle/guard checks. Quarantine permits authorized read/replay while denying new effects.

`history.append_company_event(*, actor, company, event, subject_type, subject_id, operation_id, details)` runs within the command transaction while Company is locked. Company chains use an explicit scope discriminator and never attach to a Project chain. Existing Project event payloads and hashes are preserved. Their current chain head now uses a locking read. `api.company.operation` and `api.company.history` provide Company-only readback; history uses bounded permission-first keysets, optional exact counts and current module/native source readers.

The migration adds explicit scope metadata and a unique duty digest. The digest closes SQL NULL uniqueness ambiguity for Company duties. Existing Project duty, receipt and event metadata is backfilled without rewriting original receipt hashes or event payloads. A before_migrate hook refreshes Frappe's cached module map through its supported API, so newly shipped modules are included in standard DocType synchronization; Frappe remains responsible for Module Def rows and table creation.

Canonical Company documents and estimates are separate domain prerequisites. Their owners extend existing Document/Revision/File and estimating services with immutable explicit Company scope and distinct Company duties. They do not create placeholder Projects, duplicate storage or clone the estimate library. Existing Project behavior and current cited-source authorization remain required. Company approval actions are not registered in this increment; pre-award estimate acceptance and proposal issue follow their domain prerequisites and extend the same canonical packet engine after the next checkpoint.

The operator fixture helper `grant_synthetic_company_duties(user, company, abilities=None)` grants only declared Company duties to an existing explicit identity. It does not reseed a site or change credentials/sessions. The targeted Company suite provisions isolated users and rolls its fixture transaction back.
