# Qualified R0 approval action

`project.status.change.v1` is the original R0 manifest/effect action. An immutable policy revision identifies the independent-human review rule and its synthetic scope. The immutable packet binds company, standard Project identity/version/status/completion fields, full sorted standard Task identity/status/version/progress/weight inventory, requested status, predicted native completion fields, requester person, exact policy revision/hash, and 24-hour expiry. The public response supplies the exact from/to status, native completion result, Task count, and explicit empty Task changes.

Open and On hold Projects may request supported transitions; Completed and Cancelled cannot reopen in this release. Completing a Project requires every Task to be Completed or Cancelled. Native ERPNext completion calculation is predicted using the pinned controller rules and checked after the actual standard Project save. A native outcome different from the manifest rolls back. The Project action never cascades a Task change.

Requesting a packet and granting/rejecting/withdrawing it append governance/history records and command receipts; they do not change Project status. An independent canonical human person with current scoped approval.decide duty may review from a live cookie-backed interactive session. An alias of the requester remains the same person. Service identities, API-token-only calls, workers, and model tools cannot grant. No review action is registered in Ricky's tool set.

The requester consumes an independent grant using current approval.execute and project.write duties. The service rechecks current reviewer identity/human status/review duty, current policy, expiry, exact Project version and Task inventory. The Project effect, immutable consumption, history and command receipt share one Frappe transaction. A failed save or history append leaves the grant unconsumed. An exact canonical-person operation retry returns its original success even after consumption or Project closure, while current access remains required. A different operation cannot consume the same packet twice. Generic Project status saves require an exact server action context tied to this packet, action, Project, source version and target status.

Financial submit/cancel and imported submitted docstatus are blocked for the catalogued standard Sales/Purchase Invoices, Payment/Journal Entries, Purchase/Sales Orders, Purchase Receipts, Delivery Notes, Stock Entries and Expense Claims. Their approval manifests/effects are unqualified. This release makes no financial approval, posting, payment or QBO qualification claim. Future actions must define their own immutable sources, policy, exact effect, atomic grant consumption, correction and current-authority checks; callers cannot supply a Python method or global approval bypass.

The synthetic seed adds Jordan Chen as independent reviewer for the main synthetic Project. Morgan's aliases share one requester person; Taylor remains the unrelated-project outsider. Credentials are operator supplied and never returned by the seed.

## Additive domain actions

The same packet, decision, state, independent-human review, consumption and receipt functions now support the literal `calibration.verify.v1` and `contract.baseline.activate.v1` actions. `domain_approvals.py` imports only their explicit server callbacks. Each domain owns its exact source manifest, current and historical source authorization, and apply function. The server packet wraps the raw domain manifest; the apply callback receives the original raw manifest unchanged. The active effect context binds packet, action, Company, Project, subject and manifest hash. Domain controllers require that exact context. No caller supplies a Python method or a generic trusted-write grant.

The additive request endpoint is `api.approvals.request_action(company, project, action, subject_id, expected_version, operation_id)`. Existing read/list/decide/execute/withdraw signatures continue to serve all registered actions. Project-status packet fields remain their original shape; domain packets expose the exact `review_manifest` containing subject, sources, effect and summary. Current domain-source permission is checked before historical packet/receipt replay, including after consumption and after later draft changes. Independent reviewer read rights are rechecked at grant consumption. Domain eligibility/version checks apply only to a new effect; an authorized successful logical operation returns its original receipt.

No Company approval handler is registered yet. Canonical Company documents/estimates and their own domain actions must qualify first. No registered action posts a transaction, pays money, issues a legal instrument or sends an external message.

## Closed native financial writers and admission

The unqualified native writer catalog is Sales Order, Sales Invoice, Delivery Note, Purchase Order, Purchase Invoice, Purchase Receipt, Payment Entry, Journal Entry, Stock Entry, Expense Claim, Timesheet and Material Request. Optional absent modules remain absent. Opportunity, Quotation and ordinary Company bootstrap are excluded. Guards cover insertion, pre-validation, draft save/update, submit, cancel, update-after-submit and deletion; even the internal generic trusted-write context cannot bypass them. This prevents an admitted application writer from racing the initial construction-baseline scan.

A future qualified financial/procurement writer must add its exact reviewed effect context and acquire the same declared aggregate/admission lock before changing a counted obligation or its scope. Direct host administration and raw SQL are outside application concurrency guarantees. Timesheet and Material Request presence is a conservative unqualified activity signal, not proof of certified, billed or paid quantities.

## History metadata rights

A history reference is not a source permission. The literal history dispatcher uses the exact stored source/revision and current domain/native rights before returning an item, exact count or cursor. Approval events use their stored domain manifest. Existing construction revision events identify their immutable revision in details.record_id, which is authorized separately from the mutable contract header. Unknown subjects and cross-scope references are closed. Bounded authorization scanning fails without partial results when its limit is reached. Stored events and hash chains are unchanged.
