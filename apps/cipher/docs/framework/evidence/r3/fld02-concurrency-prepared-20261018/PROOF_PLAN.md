# Local native proof plan — all cases UNRUN

The local root admits one case at a time on its existing isolated READ-COMMITTED profile. Preserve Candidate 4, the stable trial and unrelated site state. Do not reset/reseed an existing profile or reuse/restore a changed duty as part of this driver. The root supplies existing synthetic principals, explicit duties, a registered device, actual source documents and the exact staged capture where required. Fixture preparation is a separately owned transaction, outside this driver and outside a native test-case savepoint.

1. Verify the exact copied Candidate 5 files against `SOURCE_CONTRACTS.json` and the root's complete app/build manifest. Inspect the installed Frappe 16.52.0 runtime, MariaDB connection configuration and physical Python path. Build a complete manifest of actual app bytes and the selected native runtime dependencies, including any pre-existing loaded bytecode. Keep native source configuration/provider mode unchanged. Set no isolation on existing transactions or servers.
2. Admit one private root lease for the current runtime/build/epoch, stable artifact journal directory and exact finite request. Capture the pre-existing baseline outside the driver too. Lease validity is at most one hour, each attempt at most 120 seconds, SQL/lock waits at most 30 seconds. Use a narrow scope and practical lower limits. The program refuses oversized source/row/File/callback closures; do not truncate them to obtain a pass.
3. For stage/apply races, declare two distinct enabled synthetic logins bound to the same canonical Person with current Field duties. Stage operation UUID differs from the capture UUID; apply operation UUID is the original capture UUID. Keep exact envelope bytes, decimals, source/revision rights and participant People. A new run ID, alias, Company or Project must not bypass a reserved Person+UUID.
4. Before releasing the barrier, require both real process baselines complete, original business receipt absent, no staged capture for stage (or exact staged/version match for apply), actual distinct physical connection IDs and current scope/identity checks. Verify `ready` and `prepared` markers against the parent go record. A baseline/precondition failure means no concurrency result.
5. Observe both process outcomes. Stage race should produce one stage receipt and one immutable capture. Apply race should produce one business receipt, one canonical Field effect/revision and the expected quantity lineage once. Compare complete native JSON facts, immutable receipt JSON/hash/request/scope, current header for the new effect, exact original revision and every quantity; compare full before/after Task/Project/documentary/File byte/callback inventories for unrelated effects. Counts alone are insufficient.
6. Accept only outcomes supported by actual source locking: one writer with an exact canonical replay may occur; a losing apply can instead return `stale_offline_capture` before reaching the locked original-receipt check. SQL timeout/deadlock or interrupted connection is not proof of replay or noncommit. Record exact exception class/code and rollback evidence where available. Keep the original UUID and inspect it explicitly after resolution. Do not add retries to force a particular interleaving or outcome.
7. In change-before-apply, verify B's exact native target preimage and durable postimage/commit marker before A enters apply. The current binding/duty refusal must occur with no new Field receipt/effect. The marker identifies the same run/epoch/UUID/body and B connection. Reassignment uses only a declared existing distinct Person. Root must inspect whether the disabled duty was actually the necessary authority: another existing explicit grant may still permit the command, so unrelated duty disable is not a rights-revocation proof.
8. In binding/duty races, compare observed row-lock ordering, native postimages and service rights revalidation. Do not infer serialization from a Person lock: the existing identity/duty controller does not automatically acquire that lock. A writer that legally acquired/revalidated authority first differs from a command admitted after a completed revocation. Any wrong-Person, wrong-scope or post-revocation write requires root escalation, not weaker guards. No reset/restoration occurs automatically.
9. After unknown response/commit status, preserve all journals, partial Files/evidence and the global reservation. With a new current lease for the same runtime, request, run ID and journal directory, use explicit `--reconcile` only. Verify the fresh observation has no writes and unchanged callback queues; compare its canonical receipt to the original Field records. It must preserve current-rights denial. Missing/inaccessible receipt, timeout or observer failure never establishes noncommit. The original unknown reservation remains blocked even if the root later establishes the committed outcome.
10. Inventory source Files before and after by full document/attachment mapping, SHA256, exact bytes and lengths; retained source bytes must be unchanged. Verify normal Field writes produce only their expected history/offline event/receipt changes. No Task, commercial, finance or provider action is an expected side effect. This driver inventories scoped Task/Project/documentary state and the command call surface; separate finance/installation-wide effect checks remain the local owner's proof obligation, without running blocked finance/award paths.

The root's acceptance receipt must retain exact interpreter/runtime/build/site/current epoch, source manifest digest, actual connection/version/isolation readbacks, barrier and child journals, full complete before/after inventories, canonical comparisons, error classes/codes, expected/observed native record differences and unknown classifications. Driver output alone never declares acceptance.
