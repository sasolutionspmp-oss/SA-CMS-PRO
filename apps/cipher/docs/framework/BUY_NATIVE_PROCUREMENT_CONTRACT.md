# BUY-01–03 pinned native procurement contract — source audit

Audited installed ERPNext16.51.0/Frappe16.52.0. Paths below are relative to `erpnext/`. No controllers, writer guards, masters, stock, GL, portal users, suppliers or communications were changed. This is source qualification only; the runtime proof gates below remain delivery work. Preserve approved dependency order **PRJ-02 → BUY-01 → BUY-02 (also FIN-01) → BUY-03 (also DOC-01)**. A source audit does not release a writer or satisfy these work packages.

## Native document chain and source preservation

Reuse `Material Request` → `Request for Quotation` → `Supplier Quotation` → `Purchase Order` → `Purchase Receipt` and their standard child tables. Keep standard Supplier/Item/UOM/Price List/Currency/Warehouse/Account/Project masters. A Cipher procurement package and immutable supplier-response/comparison revisions carry AEC scope/WBS/cost coding, quote-original artifact citations, selection rationale, exact unit/currency normalization, exceptions and independent decisions. They do not create duplicate Suppliers or a second purchasing ledger.

Native mappers are useful only when their actual source standing is supported and authorized; never turn a draft into submitted standing merely to make a mapper work. Material Request→RFQ (`stock/doctype/material_request/material_request.py:845–878`) requires submitted `material_request_type=Purchase`, maps request/item lineage and `project` to RFQ line `project_name`, and selects the still-unordered/requested quantity. MR→PO at648–725 requires submitted Purchase/Subcontracting and applies requested/mapped quantities. RFQ→Supplier Quotation (`buying/doctype/request_for_quotation/request_for_quotation.py:459–496`) requires submitted RFQ, maps RFQ line IDs and project, and can infer currency/price list from Supplier. Supplier Quotation→PO (`buying/doctype/supplier_quotation/supplier_quotation.py:245–301`) requires submitted source, maps Supplier Quotation/line and Material Request lineage, copies taxes, sets missing values and totals, and explicitly has **no quantity tracking between supplier quotation and PO**: it only deduplicates already-mapped row references. Cipher must enforce its own approved allocation/award quantity across multiple orders. The supplier-quotation mapper also validates submitted docstatus but has no current-date expiry check in that function; Supplier Quotation.validate_valid_till only rejects validity earlier than its own transaction date. BUY-02 must independently bind and check current quote validity or a specifically authorized supplier-confirmed extension. Submitted status alone does not mean an expired vendor quote can be ordered today.

An immutable vendor-original file/revision is retained even when its parsed/normalized quote changes. Each comparison row pins original Supplier Quotation revision/snapshot, supplier item description, quantity, quoted UOM, exact rate/currency, freight/tax/lead-time/inclusions/exclusions/validity, normalization policy, exact conversion and original artifact citation. Native Supplier Quotation may be editable while draft; if Cipher preserves that draft convention, independent PO creation must use an approved immutable response snapshot and custom provenance rather than point native source fields at a newer mutable original. If the supported submitted quotation workflow is chosen, use its real native submit/cancel lifecycle and pin exact saved native child IDs plus Cipher line UUIDs. Neither path permits updating original quote bytes or claiming a normalized total was the supplier's original amount.

## BUY-01: requests, RFQs and quote comparison

Material Request required native header fields are naming series (`MAT-MR-.YYYY.-`), request type, Company, transaction date and Items. Each item requires real Item, quantity, stock UOM, entered UOM, conversion factor and schedule date. Admit Purchase only initially; manufacture/subcontracting/transfer/material issue/customer-provided types have separate stock/work-order consequences and are not interchangeable AEC service requests. Native validation (`material_request.py:182–224`) checks schedule, open related Sales Order, references, integral UOM quantities, request type and item facts. Submit at334 updates production-plan/requested quantities and relevant previous-document standing; it can validate a native Budget for Purchase. Cancel at393 reverses request/plan status and requested quantities. A “request” is therefore not free of operational side effects after native submission.

RFQ header requires naming series (`PUR-RFQ-.YYYY.-`), Company, transaction date, Suppliers, Items, subject, status, and either message text or HTML according to `use_html`. Supplier rows require existing Supplier. Item rows require real Item, quantity, schedule date, stock/entered UOM and conversion. Native `request_for_quotation.py:82–159` checks duplicate suppliers, frozen/disabled/prevent-RFQ supplier standing, quantity and Item facts, and calculates stock quantities. Native required quantities can be zero only under the explicit unit-price setting; initial Cipher scope should reject that mode until a precise policy exists.

**RFQ submit has external and identity side effects.** `on_submit` at175 sets Submitted and quote statuses and immediately calls `send_to_supplier`. Supplier `send_email` defaults to1 in installed metadata. At207–310, enabled rows with an email validate recipients, may create Website Users/Contacts/Portal User links, and send/queue supplier email; this is not merely preparing a draft. Local qualification must explicitly set every supplier `send_email=0`, prohibit direct send routes, and prove no Email Queue/Communication/User/Contact/PortalUser change. Formal distribution is a separate exact-recipient/artifact command through a qualified durable outbox/provider with current authority and recovery/readback. Do not enable native automatic sending or implicit supplier-user onboarding as a side effect of the procurement approval. RFQ cancellation only marks Cancelled; it cannot retract mail already sent.

Supplier Quotation requires naming series (`PUR-SQTN-.YYYY.-`), existing Supplier, Company, transaction date, currency/conversion and Items. Lines require native Item, quantities, UOM/conversion and native base rate/amount. `supplier_quotation.py:117–175` validates Item/reference/UOM and validity (valid_till cannot precede transaction_date). Submit/cancel at132–139 updates RFQ supplier quote standing. Supplier portal creation (`request_for_quotation.py:499–529`) is a separate upstream endpoint using portal membership and `ignore_permissions`; do not expose it through Cipher's ordinary RPC catalog. The existing closed catalog must continue blocking generic mappers and portal routes unless their exact native/domain authorization is reviewed.

## BUY-02: native PO plus construction commitment

PO requires native naming series (`PUR-ORD-.YYYY.-`), Supplier, Company, transaction date, currency/conversion, nonempty Items and native status. Lines require existing purchase Item and name, scheduled date, quantity, stock/entered UOM, conversion factor, base rate/amount; Material Request and row IDs must be supplied together if used. Supplier/item must be enabled and permitted for purchase, with Company defaults/current native rights; supplier Company account association, native account visibility, qualified UOM revisions and supported Price List/currency are explicit prerequisites. No Item/Supplier placeholder is created for an unrecognized quoted line. The line's Project/WBS/cost code/type and accepted budget/contract/SOV line allocation must be exact and in the same Company/project. No manufacturing Subcontracting Order stands in for a construction subcontract.

`purchase_order.py:199–280` runs native BuyingController validation, supplier rules, schedule, Item facts, closed MR checks, integral UOM/stock quantity, reference matching, minimum order quantities, native intercompany and subcontracting behavior. Source checks compare Supplier Quotation Supplier/Company/currency and line Project/Item/UOM/conversion; MR Company and Project/Item also match. Native `maintain_same_rate` can add a reference-rate restriction. Initial scope excludes intercompany, supplier delivery/drop ship, bundles, assets and manufacturing subcontracting unless separately admitted; these can create additional records/effects.

Bind exact money as canonical decimal strings and quantities as explicit qualified decimal/rational conversions. A no-FX/no-tax first policy requires source Supplier price currency == Company base currency and conversion1; preserve source quote currency independently even if normalization is required for comparison. Native missing defaults, taxes and rounding must run, then persisted SQL Decimal quantities/rates/amounts/base totals/taxes/discounts must reconcile to approved facts. No silent FX, freight inclusion, rate substitution or binary-float rounding of a contractual amount. A tax-capable PO release needs an explicit current tax/account/valuation policy, not a guessed tax template.

Native submit at483–509 updates previous request/quotation status, requested/ordered quantities, native budget checks, reserved subcontract quantities, approval controls, blanket/intercompany links, and can automatically create subcontracting orders. Native cancel at510–547 unwinds permitted status/bin/previous-document/link effects and may affect drop-ship Sales Order received standing. POs are commitments, not supplier payables; neither native PO creation nor `Cipher Commitment` may manufacture a Purchase Invoice/GL liability/payment. Submit/cancel/edit-after-submit have distinct exact registered policies and dependent-receipt/bill checks; editing a current PO cannot rewrite an executed commitment original.

`Cipher Commitment` uniquely links the real PO to a qualified construction contract, its immutable accepted terms/SOV and exact authorizing package/quote/award/budget allocation. Native PO/line custom provenance should reference the canonical commitment and stable Cipher line UUID; the sidecar pins source quote revision/hash, original Company/awarded Project, native PO/line names and saved versions, authorized quantity/value/currency and change lineage. FIN-01 currently treats native PO/MR/receipt activity conservatively as unqualified. BUY-02 must register recognized commitment/PO effects and declared floors with FIN before enabling the writer, with the same admission lock and monotonic certified/billed limits. Do not merely permit drafts while leaving zero-activity admission assumptions unchanged.

## BUY-03: goods receipt, inspection and stored materials

PO→Purchase Receipt mapper (`purchase_order.py:813–875`) requires an actual submitted PO. It uses pending native quantity (`PO.qty - PO.received_qty` plus staged mappings), excludes supplier-delivered rows, maps exact PO/item and request/Sales Order lineage, copies/reset taxes and runs missing-value totals. It does not independently certify AEC installation, lien/title ownership or invoice eligibility.

Purchase Receipt header requires naming series (`MAT-PRE-.YYYY.-` or return series), existing Supplier, posting date/time, Company, currency/conversion, Items, base net total and native status. Lines require real Item/name, received quantity, stock/entered UOM, conversion and base rate; accepted `qty`, rejected_qty, accepted/rejected warehouses, exact PO/row, quality inspection and serial/batch data have additional conditional validation. Native validation (`purchase_receipt.py:263–355`) checks posting date/time, PO date/open status, required PO according to Buying Settings, references, integer UOM quantities, quality-inspection reference identity, CWIP/provisional accounts, stock/warehouses and no future posting. Native receipt requires PO if `Buying Settings.po_required=Yes`; Cipher's initial project goods path should require exact qualified PO regardless of a looser native setting.

Native quantity meanings are critical: **received_qty = accepted qty (`qty`) + rejected_qty** (`controllers/buying_controller.py:795–808`). Received stock quantity and accepted stock quantity are separately derived from conversion factor (`buying_controller.py:760–784`). Accepted material goes to its accepted warehouse; rejected stock needs a distinct rejected warehouse (`controllers/subcontracting_controller.py:112–126`, inherited here). Rejected material creates stock-ledger movement in that warehouse; valuation depends on `Buying Settings.set_valuation_rate_for_rejected_materials` (`buying_controller.py:963–980`). Native PO status updater uses PR **received_qty**, including rejected units, for PO.received_qty (`purchase_receipt.py:159–179`). Therefore native “remaining to receive” is not “remaining accepted for use.”

Example proof target, not a performed test: order10; receipt delivered6/accepted5/rejected1 yields native received6 and pending4, accepted usable5, quarantine1. A second delivered4/accepted4 yields native pending0 but usable9/quarantine1. A replacement cannot be silently treated as an additional native pending unit; execute the appropriate governed rejected-material return and replacement or explicit quantity-amendment policy. Track cumulative delivered, accepted, rejected, returned and installed quantities independently, with stock-UOM conversions and unambiguous eligibility. Native `Stock Settings.over_delivery_receipt_allowance`, per-Item allowances and override role can permit excess receipt (`controllers/status_updater.py:418–466`); a Cipher grant must bind its own allowed quantity and current allowance policy and must not inherit a broad native override role as commercial approval.

Quality Inspection references must match exact Purchase Receipt and Item (`purchase_receipt.py:353–371`); actual Item-required inspection/quality disposition must be qualified. A pypdf delivery-ticket upload is evidence, not a stock receipt or accepted quality decision. `Cipher Receipt Evidence` pins receiver/canonical person, delivery ticket/document revision/hash, actual date/location, native PR/line, exact delivered/accepted/rejected quantities, inspection/disposition and commitment/PO/source-line lineage. A `Cipher Stored Material Lot` adds title/ownership, custody, location, insurance, contract stored-material eligibility and applicable hold evidence. Receipt/warehouse presence does not itself satisfy a stored-material billing clause or confer title.

A physical material receipt is **not** `Cipher Installed Work Certificate`. Installation needs separately reviewed measurement, location, work/contract/SOV line, responsible person and nonduplicated certified quantity/value. A supplier service/work certificate cannot be faked as receiving an inventory Item or by setting stock warehouse quantities. Native non-stock receipt support can be an operational delivery acknowledgment under a qualified policy, but remains separate from installed-work acceptance and subcontract application/payment/retainage.

## Stock, GL and QBO authority

`PurchaseReceipt.on_submit` (`purchase_receipt.py:388–412`) updates native PO/request/billing standing, serial/batch bundles, stock ledger, GL entries, future stock/GL reposting, subcontract quantities/reservations and production-plan received quantities. Cancel at464–485 reverses stock and GL, reposts future valuations and updates related quantities; `before_cancel` also changes linked invoice amount-difference data. Cancel is not deleting a receipt and cannot erase an already-invoiced/consumed stock or settled obligation. Supported returns use native return documents (`purchase_receipt.py:1708–1718` and `controllers/sales_and_purchase_return.py:549`), with original-return linkage and eligible quantities; rejected-warehouse returns have a specific supported mapper.

**Purchase Receipts can create GL before supplier invoice.** `controllers/stock_controller.py:333–360` runs GL when perpetual inventory needs stock-account mapping, when Company provisional accounting for non-stock items is enabled, or for asset receipts. `purchase_receipt.py:770–807` records stock/asset received-not-billed and can create provisional non-stock expense entries; taxes/landed costs also affect valuation/accounts. Merely asserting “we are only receiving, not posting AP” is false under those configurations. Serialized/batched items, valuation methods, backdated/future reposting, assets/CWIP and subcontracting add further native consequences.

The approved accounting architecture is settled: **ERPNext is the sole operational ledger and QBO is the official accounting book** (framework ADR-004 and posting-class map). Configured receipt valuation and native GL are intentional supported ERPNext behavior, not a platform blocker or a reason to reopen that choice. A committed local operational posting and an acknowledged official QBO effect are separate standing and must be shown separately. Before the first submitted receipt, bind the selected Company valuation/perpetual/provisional/asset policies, native account mapping, period, exact expected stock/GL effect and official export/reconciliation treatment. Choose one supported creator per transaction class: an official accrual/stock asset mapping and later invoice clearing must not export the same receipt as expense and then export the full invoice as a second expense. Do not disable perpetual inventory globally or hide native GL to make a fixture appear harmless. If the selected accounting policy cannot be qualified, keep PR submission unavailable while still allowing truthful preparation/inspection evidence. BUY-03 does not authorize Purchase Invoice, payment, retainage posting or external QBO writes; FIN-02 follows its declared prerequisites.

## Authorization, locking, guards and proof gates

Require current canonical person/binding/User, a mandatory matching Company and exact applicable duties in the declared real awarded Project scope, current native create/read/submit rights, native Supplier/Item/UOM/Currency/warehouse/account visibility and exact source-document/contract rights. Project duties never imply Company-only authority or cross-company supplier/item rights. A separately exposed Company-scoped master workflow requires its own exact Company duties; do not demand or infer a Company-wide grant merely to perform an authorized Project-scoped procurement action. Historical comparisons, commitment receipts and receipt evidence reauthorize exact original sources before metadata, count/cursor or artifacts; idempotency is not permanent access. Quote/warehouse/account native changes invalidate new-effect manifests, while historical authorized originals remain immutable.

Keep existing closed Material Request/PO/Purchase Receipt guards at all current native write phases. Before any newly supported RFQ/Supplier Quotation writer is exposed, add narrow linked-record guards as well as the closed ordinary RPC catalog; upstream portal/mappers/send/update-status paths are not automatically safe. Each allowed operation needs a literal registered server effect context binding action/subject/source revisions/target Company+Project/document IDs and native payload. Generic trusted_write cannot authorize arbitrary procurement documents, submit, cancel, send or return. Native direct `db_set` status/bin/item updates performed inside qualified controllers must be enumerated and reviewed; known RPC catalog protections remain necessary.

Use the established canonical participant Person→identity/User→declared aggregate/admission locks→sorted qualified UOM→Currency→sorted native Item/party references order. FIN party-channel scans cover Company+Supplier across Projects, so Project locking alone does not serialize a second PO/receipt for the same Supplier elsewhere. Future supported party-channel writers must hold the same exact native Supplier row that FIN locks, after UOM→Currency in the sorted native source union, and use current locking admission reads before effects. Project-only MR activity shares the Project mutex; unrelated ambiguous Company-only channels stay closed until their own declared lock exists. Do not introduce a late Company lock after Project as a shortcut. Add deterministic contract/commitment/PO/receipt/warehouse locks where needed, sharing FIN admission locks before supported draft/posted obligation writes; do not introduce warehouse→Project or supplier→UOM inversions. Commands apply current versions, exact effects, consumption, receipt/history and durable outbox intent in one local transaction with same-person UUID conflict/replay semantics. Roll back all stock/GL/sidecars if exact native reconciliation or a late source/permission check fails. Remote send/export never occurs inside that transaction.
