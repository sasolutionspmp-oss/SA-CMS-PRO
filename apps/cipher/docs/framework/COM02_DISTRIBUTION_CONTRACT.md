# Governed proposal distribution and durable local delivery contract

Status: controlled synthetic qualification. The literal action has been released for isolated fixture activation after the supported migration; full grant/worker/HTTP and persistent-consumer evidence remain separate gates. This document does not enable an action, install a policy, transmit a message, or qualify an external provider. COM-02 Issue creation must qualify before distribution is released. The first transport is an independent durable synthetic fixture sink. A committed local receipt must be labeled fixture acknowledgment, never email delivery or recipient acknowledgment.

## Ownership and boundaries

Shared backend owns integrations/distribution services, the literal approval registry entry, explicit Company command/receipt/history routing, canonical integration operation extension, API/schema registration, migration and worker dispatch. DOC owns commercial Issue/source readers and supplies exact immutable Issue/PDF/source/native authorization. QA owns independent fault injection and sink-readback proof. UI consumes fixed typed routes after publication. Root owns deployment, persistent fixture sink storage, worker/HUP/migration sequencing and runtime evidence. Astra reviews the grant, authority, retry and source boundaries.

Preparation, Issue and distribution remain three commands. Native Quotation remains a draft. Distribution never rerenders, edits an Issue, selects a newer PDF, creates a Sales Order, changes accounting or contacts an unconfigured provider. No generic handler name, arbitrary DocType, outbound URL, filesystem path, email configuration or model-selected transport is accepted from callers.

## Fixed action and scope

The action is `proposal.distribute.v1`, subject `Cipher Distribution Instruction`, Company scope only, project null. It uses the existing Packet/Decision/Consumption engine. Request creation requires exact Company commercial.read, document.read and commercial.write. The exact Company ability `commercial.distribute` authorizes distribution request/execute in addition to approval.request/approval.execute; commercial.write alone does not confer it. Review requires current independent Human canonical Person, real interactive review, approval.decide and commercial.read/document.read/native Issue source rights. The requester cannot review through an alias. No model, service identity or worker can grant.

The action was staged disabled during source/migration review. Its controlled synthetic activation installs only the exact Company policy and grants commercial.distribute only to the named isolated fixture author. The profile remains unavailable unless the operator explicitly enables it. Activation alone is not delivery qualification. The exact Company duties never grant Project rights or inherit from Project duties.

The static adapter is `integrations.distribution_governance.{approval_manifest,authorize_subject,apply_dispatch}` using the existing keyword-only actor/company/project/subject_id/phase/lock/manifest/scope_type interface. The raw manifest has subject/sources/effect/summary. `authorize_subject(..., manifest=stored_manifest)` checks the original immutable Issue/PDF/message/profile rather than the current proposal working head. `apply_dispatch` requires the exact packet/action/instruction Company effect context. No generic trusted-write exception suffices.

## Immutable instruction

`Cipher Distribution Instruction` is an immutable server-authored Company record. It stores UUID identity, scope_type Company, company, null project, canonical author, exact Issue ID and digest, the immutable Issue linkage to Proposal Revision/digest, prepared Document/Revision IDs, exact SHA-256, byte size, media type, immutable recipient array, message fields, selected server-owned profile ID/version/facts and creation/session metadata; the Company command receipt/history preserves its operation identity, body JSON and body digest. Its body is constructed from current authorized scoped readers and validated again by its controller. Native JSON list/get/export routes remain denied; fixed scoped APIs reauthorize every source.

Recipient identities are SHA-256 digests of the exact originally issued recipient rows (name, email and organization). The first slice accepts the full issued set or an explicit subset of those identities, without address additions, normalization changes or rewritten names. A recipient addition or address change requires an authored successor prepared/issued revision. First profile supports a single synthetic fixture channel, not a real mail address delivery route. The issued recipient set already excludes duplicate addresses, and distribution additionally refuses duplicate selected recipient identities. Limits are explicit (30 recipients, subject 240 characters, body 20,000 characters, no caller HTML or arbitrary attachments). The attachment is exactly the issued prepared PDF. Recipient/message/cover semantics must agree with the immutable issued recipient/output contract; any permitted change requires a new independently reviewed distribution instruction. A changed prepared PDF requires a successor Proposal Revision and Issue according to COM-02, never a rewrite.

The versioned instruction contract digest covers Company, exact Issue/source identifiers and digests, PDF identity/hash/size/type, ordered recipients, exact UTF-8 message subject/body, the complete fixed profile facts and explicit authorization validity. expected_version in request_action is the instruction digest. It is never a mutable current-head timestamp.

Profile IDs resolve through a literal server registry. Initial profile `local-fixture-v1` exists only on an explicitly synthetic site, uses persistent independent sink storage and has a bounded payload size. API responses label mode `fixture`. No SMTP/HTTP endpoint or credentials are provisioned by this slice. Profile disablement/revision invalidates unused authorization; a worker never silently chooses a substitute profile.

## Atomic authorization consumption and intents

Consumption creates one immutable `Cipher Distribution Dispatch` per instruction and one canonical `Cipher Integration Operation` per exact recipient in the SAME Frappe transaction as Consumption, history and command receipt. Unique instruction→dispatch prevents a second packet from dispatching the same instruction twice. Per-recipient delivery identities are UUIDs assigned server-side at dispatch, not reused browser operation IDs. The existing global canonical Person+operation UUID namespace applies to create_instruction and approval execute across every Company/Project command.

The dispatch snapshots instruction digest, Issue/PDF digest, packet/decision/grant hashes, requester/reviewer canonical Persons and original User bindings, explicit Company authority, profile and recipient operation IDs. Each operation binds dispatch+recipient identity, original payload hash, exact PDF hash and a transport idempotency key. Retries preserve all these fields. Aggregate state is derived from recipient outcomes: Queued, Unknown, SucceededFixture, PartiallySucceeded, Cancelled or Failed; individual Claimed preflight state remains visible on each recipient. Individual recipient outcome is always visible. No aggregate success is inferred from enqueue or local transaction commit.

The existing Project task.create operation payload/hash/receipt behavior is preserved. Canonical Integration Operation and Delivery Attempt gain additive explicit scope metadata, defaulting old rows to Project without changing payloads or result bytes. Company uses project null only through a literal Company enqueue path. Both after-commit publication and scheduler recovery route the literal distribution kind to the fixed cipher_distribution RQ queue; Task operations remain on short. QA first runs a controlled burst/manual consumer, then root qualifies a persistent consumer and restart recovery before claiming automatic local delivery readiness. The dispatcher routes this literal kind to a dedicated worker; it does not accept an arbitrary callable. Existing outbox claim/fence semantics remain, with current source and authority guards added for this public durable command.

All participating Person locks precede User/Identity and Company, then declared domain/source locks. Issue/PDF and native source readers must reuse the documented UOM→Currency→sorted native references order; the worker cannot lock an operation then wait for Company while interactive dispatch holds Company and waits for that operation. Claim transactions are short and independent; the delivery/effect phase reacquires scope/authority before its operation fence, or uses a reviewed equivalent order. No remote call is made while holding Frappe transaction locks.

## Durable business authority and revocation

This is an explicit durable business authorization, separately reviewed and consumed through the independent approval engine. It is not an extension of an ordinary browser or Ricky session. Browser commands and Ricky effects retain their existing session expiry/revocation checks. The distribution instruction records the original creation-session reference; dispatch records the executing and reviewing session references and the original User/canonical Person bindings. No bearer cookie is stored.

A consumed dispatch has its own immutable not-after (the earlier of instruction lifetime and packet expiry), exact Issue/PDF/recipient/message/profile scope, current identity/duty/source/policy checks and cancellation record. Within those boundaries it may outlive ordinary browser logout. This narrow durable business mandate was explicitly approved by the orchestrator for this exact dispatch. It does not qualify session reuse by other commands, Ricky, generic jobs or a future external provider.

The irrevocable attempt boundary is the commit of a current-authorized Unknown attempt with a short absolute attempt_not_after, before the independent sink call. Revocation, cancellation or quarantine observed afterward cannot recall an already in-flight attempt; it prevents a new one. The sink refuses a NEW acceptance after the attempt deadline. Recovery readback remains observational even after the mandate expires or authority/profile is revoked: an exact original acknowledgment may still be recorded without exposing its private payload publicly. Unavailable readback remains Unknown; it is never labeled not-sent or Failed merely because authority expired. Authoritative absence serializes with sink acceptance using BEGIN IMMEDIATE, so a transaction that passed its deadline check cannot later commit behind an allegedly definitive absent result.

`cancel_dispatch` is a scoped command for the original requester with current commercial.distribute/source rights. It creates an immutable cancellation; remaining not-started recipients are stopped. Already authorized in-flight attempts may complete, and their immutable acknowledgments/readback facts survive cancellation. The response states in_flight_may_complete explicitly.

Revocation/quarantine before transport blocks undispatched recipients, leaves immutable intents and safe failure evidence and performs no sink write. Source checks use current locking reads under MariaDB REPEATABLE-READ, not an earlier ordinary snapshot. The restored-site execution quarantine guards instruction new effects, packet consumption, scheduler publication and worker transport. Record read/history remains subject to current exact source rights. Completed receipt replay never grants permanent access to an Issue or PDF after rights are revoked.

## Independent synthetic sink and ambiguous outcomes

The local fixture sink is a separate process/database, not another row in the same Frappe transaction. Implemented fixture storage is SQLite with full synchronous durability and a unique transport idempotency key, storing exact original payload hash, attachment hash and bytes, recipient/message digest, acknowledgment ID and timestamp. The fixed server path is site/private/distribution-fixture/receipts.sqlite3 in the persistent private site volume; callers and profile flags cannot redirect it. Root owns deployment and backup of that storage. The first implementation uses a literal process adapter, no network transmission. Existing pre-distribution restore evidence does not qualify live-copy consistency of this new SQLite file: backup must quiesce its attempts or use SQLite backup semantics, preserve original keys and retain restored-site execution quarantine pending reconciliation. Sink tests open/read the independent database in a separate connection/process.

`deliver(key, payload, pdf_bytes)` verifies byte hash and size. A first key commits exactly one durable receipt before acknowledging. Repeated identical key/hash returns the original acknowledgment. Same key with different payload/PDF is a permanent integrity conflict. `readback(key)` returns absent, exact original receipt, or a typed unavailable result. It must not inspect Frappe operation state to decide success.

Worker transport occurs after durable claim and current authorization validation, with original key. If the sink commits then the process dies before Frappe acknowledgment, recovery performs readback using the SAME key. An exact receipt reconciles to succeeded_fixture; absent permits a same-key retry; unavailable remains uncertain and waits. A late worker fence cannot overwrite replacement state. Neither timeout nor a lost acknowledgment justifies a new logical delivery key. No claim of exactly-once external transport is made; local sink uniqueness+readback proves one durable fixture receipt per recipient in the qualified failure cases.

## Fixed API under qualification

Operator setup uses supported bench commands, with Python literal `True` for `--parse`:

```sh
bench --site cipher.localhost set-config cipher_distribution_fixture_enabled True --parse
bench --site cipher.localhost execute cipher_aec.governance.approvals.install_policy
```

The operator then calls `cipher_aec.install.grant_synthetic_company_duties` with the exact isolated author User, exact Company and `abilities=["commercial.distribute"]`. This is a narrow fixture extension; it does not reseed, change passwords or grant a Company-wide team implicit authority. Root reloads the coherent web source. The profile flag does not provision a persistent queue consumer; that separate worker/readback/restart qualification must complete before automatic local readiness is reported.

`integrations.distribution_api.create_instruction(company, issue_id, recipient_ids, subject, body, profile_id, operation_id)` POST returns instruction+original command status. IDs/profile are server-validated; instruction version is its digest.

`get_instruction(company,instruction_id)` GET, `list_dispatches(company,issue_id,limit=50,cursor=None,count_mode='none')` GET, `get_dispatch(company,dispatch_id)` GET and `get_recipient_delivery(company,dispatch_id,recipient_id)` GET expose authorized metadata and fixture acknowledgment/readback state. `cancel_dispatch(company,dispatch_id,reason,operation_id)` POST stops remaining not-started recipients; `profiles(company)` GET labels the fixed local profile and availability. No generic retry endpoint, direct enqueue endpoint or caller effect kind is exposed. Approval request/decide/execute/withdraw use the existing six Company APIs and exact instruction subject/version. Read-only lists authorize all bounded candidate source records before items/count/cursor. Cursor binds literal selector, Company, canonical Person/current identity, query filters and current authority.

Receipt and history dispatchers use exact Distribution Instruction/Dispatch/recipient records and original Issue/PDF source readers. Unknown types and cross-scope IDs fail closed. History stores immutable event facts; revocation filters metadata before counts/cursors without rewriting existing chains.

## Distribution-only recovery publisher

`cipher_aec.integrations.distribution_recovery.publish_pending` is a trusted operational one-shot entry. `run_forever` repeats it every five seconds for the process supervisor. It opens a fresh read-only transaction, checks uncached synthetic/quarantine configuration, selects at most 100 existing operations with exact Company scope, no Project, and kind `company.proposal.fixture.v1`, then calls the existing fixed-queue publisher with each original operation name. Eligible states are Queued or Claimed/Unknown with an absent or expired lease. Terminal operations, other kinds and Project operations are excluded. No instruction, recipient, operation, sink call or new authority is created. Each sweep clears its transaction; an existing business write transaction is refused. Quarantine is rechecked before each publication. The reported `publication_attempts` count is not a Redis acknowledgment.

The supported supervisor target is `bench --site cipher.localhost execute cipher_aec.integrations.distribution_recovery.run_forever`; a bounded manual sweep uses `publish_pending` instead. General ERPNext cron may remain paused. The literal dedicated consumer remains `bench worker --queue cipher_distribution`. Root owns process startup/restart and qualification; adding these entries does not itself prove runtime automatic recovery. Existing Task publication is unchanged.

A real acceptance must distinguish a stopped consumer with an already-published RQ job from failed after-commit publication with only a committed database intent. For the latter, the operator preserves the site's original queue-key presence/value, temporarily changes only the site's `redis_queue` endpoint to an unreachable local endpoint through supported configuration, refreshes web processes to discard cached queue clients, consumes a legitimate grant over HTTP, and proves the database intent exists while its canonical RQ job does not. Cache/session Redis remains available. Restore the exact configuration, refresh affected processes, then let only this scoped publisher republish the original intent and prove one independent sink receipt. A publisher started under a deliberately wrong endpoint must be restarted after restoration because Frappe caches queue clients. These outage/restart checks are separate from the eight executable query/guard/configuration tests and remain runtime evidence owned by QA/root.

RQ rejects custom queue names unless native worker configuration registers them. Before launch, the supported synthetic operator helper `cipher_aec.integrations.distribution_install.configure_queue` merges only `workers.cipher_distribution.timeout=120` into common configuration, preserving other workers and existing queue properties. The development manager invokes it before child processes start. Applying source or starting a consumer does not establish queue registration or acceptance in an already-running process; root applies the helper and refreshes cached web catalogs before the actual publication proof. Operator configuration changes are serialized, and malformed existing worker configuration is refused.

Recipient IDs come from the existing deterministic server contract; callers neither hash identities nor edit/add addresses. Only this explicit inventory read root shares the approved bounded original-producer graph; all individual record checks and requested bytes remain current within the read snapshot. Actual HTTP qualification is recorded separately from the eight executable SQL/guard/subset tests.

## Delivery readback identity and historical receipt compatibility

Current dispatch/recipient reads always provide the immutable operation `logical_key` and `payload_hash`. Before reporting Succeeded, the server verifies the stored fixture acknowledgment matches those exact keys and the authorized PDF SHA/length, and verifies complete unique original-recipient inventory plus payload/index/source binding. A valid-shaped same-PDF acknowledgment for another recipient is an integrity error. Unknown/Claimed/Failed/Cancelled may retain the worker's exact `{attempt_not_after,mode}` envelope; this is attempt metadata, never acknowledgment. Missing or inconsistent operation rows do not imply successful completion. No operation, state or stored result is rewritten by these reads.

The two expected-key DTO properties remain optional only because earlier cancellation command receipts embed historical delivery snapshots. Those original receipt bytes are preserved. The UI treats absent expected keys as unverified and obtains fresh current dispatch readback before verifying identity; it does not recompute transport hashes. Current endpoints always populate both keys, separately asserted by actual response qualification.
