# PRJ-02 native Sales Order contract — read-only preparation

Verified against installed ERPNext 16.51.0 / Frappe 16.52.0. This is source qualification, not a completed Sales Order runtime acceptance or an enabled writer. No source records, guard catalog, native status, or master records were changed for this audit.

## Supported origin

Build a new ordinary `Sales Order` through `frappe.get_doc(...).insert()` and the installed standard controller, using the exact immutable approved Cipher Issue as the source. Do not call the native quotation mapper: `erpnext/selling/doctype/quotation/quotation.py:377` checks native quotation expiry, `_make_sales_order` at392 calls `_make_customer` at398, and the mapping at485 requires source `Quotation.docstatus == 1`. `_make_customer` at583–612 can implicitly create a Customer from a Lead/Prospect. Native Quotation remains a guarded mutable draft under the selected COM design.

Do not bypass mapper validation, manufacture a submitted Quotation, submit the current draft, or fill native source fields with historical pointers that actually reference a newer working draft. Leave `Sales Order Item.prevdoc_docname` and `quotation_item` empty. Native quotation-source checks compare current company/item/UOM/conversion factor (`sales_order.py:480–494`), and later submission updates referenced Quotation/Opportunity standing (`sales_order.py:504–512,519–529`). Independent creation with empty optional native quotation references avoids claiming that relationship and preserves the original draft.

The new order and a future immutable award sidecar must preserve the Company source independently of its eventual real Project. COM02 has now confirmed the canonical issued record is `Cipher Proposal Issue`, bound to immutable `Cipher Proposal Revision` and complete selected-line/native/qualified-unit/baseline snapshots. Recommended native custom links are `cipher_award` (future canonical award sidecar), `cipher_issue` → `Cipher Proposal Issue`, `cipher_proposal_revision` → `Cipher Proposal Revision`, and `cipher_accepted_baseline` → `Cipher Estimate Acceptance` when the award uses a single accepted baseline. Actual Link targets must use these canonical DocTypes, not duplicates. `cipher_issue_digest` pins issue content. Order lines require a stable `cipher_proposal_line_id` UUID and an exact award-line reference. The sidecar carries immutable Issue ID/hash, ProposalRevision ID/hash, selected source line UUIDs, accepted-estimate baseline IDs/hashes, original Company, awarded Project, explicit item/UOM mappings, quantity/rate/amount strings, selection/allocation policy, and native saved-order reconciliation digest. Multiple estimate sources for one commercial line require explicit allocation rows; a bare nullable single estimate link cannot represent them. Native Quotation Item row names are unsuitable as the only identity because subsequent draft composition can replace them.

## Canonical whole-award adoption

The current COM-02 contract permits one prepared output and one immutable Issue per exact Proposal Revision. Changing cover, recipients or renderer requires an explicitly authored successor revision. Different revisions or Proposals within one Pursuit can still produce distinct Issues, so uniqueness on Issue alone cannot prevent duplicate full award/Project/budget adoption.

For the future bounded whole-award/new-Project slice, enforce one canonical `Cipher Award Handoff` per **Company + Pursuit**, retaining its native Opportunity lineage, plus explicit unique source-line adoption identities. Also retain exact Issue/revision/baseline links and canonical-person operation replay. A second person or UUID using another successor Issue from the same Pursuit must not create another Project or adopt the same accepted source lines again. Partial/split awards and corrective reuse require a separately defined allocation/correction policy; they are unavailable in this initial contract. This is a reviewed implementation requirement, not a currently installed constraint or a runtime award claim.

Initial Project access is also an explicit reviewed award input. The selected contract requires a current exact Company delegator capability and a bounded manifest of canonical recipient Persons and exact Project abilities. All participant Persons are locked before identity/Company/Project sources; consumption rechecks delegator authority and recipient eligibility, then creates only those approved duties atomically with the real Project, award and governance history. Company roles/duties never inherit, and the creator receives no implicit administrator access. Post-commit Project access derives solely from that approved team. This is the agreed engineering contract for the future writer, not a currently enabled award or permission-administration route; see the companion [FIN admission contract](PRJ02_FIN_ADMISSION_CONTRACT.md).

The fixed future names are Company-only `project.team.delegate` and `commercial.award`, with action `award.project.create.v1` over the canonical handoff's exact immutable planned revision/digest. The one Company+Pursuit handoff aggregate owns those revisions and one full adoption. Its manifest includes exact Issue, accepted baseline/lines, existing Customer/Items, initial team and current delegation-policy revision/hash. Request/consume discover and lock the sorted requester/reviewer/explicit-delegator/all-team Person union before identity/Company; discovery grants no authority, and changed or extra participants require fresh planning. The requester needs the award ability plus explicit current delegation authority covering every chosen Project ability. Current member Company eligibility, native/source rights and policy are rechecked at consumption. These selected design names are inactive: no capability metadata, registry, install policy, API or native award writer is enabled by this audit.

## Native admission and required fields

`Sales Order` metadata requires naming series (`SAL-ORD-.YYYY.-`), existing Customer, order type (`Sales` by default), Company, transaction date, Currency, conversion rate, selling Price List, price-list currency, price-list conversion rate, nonempty Items, and native Status. Conditional transaction time applies to internal customers. New native orders remain `docstatus=0`; the controller derives `status=Draft`. Do not assign a submitted/completed standing.

`Sales Order Item` requires **existing native Item.item_code**, item name, quantity, UOM and conversion factor. This is stricter than COM-01 authored freeform quotation lines. An issued freeform commercial line cannot be silently converted into a fake Item: award admission must require an explicit existing sales Item mapping or remain unavailable until a separate visible master-data workflow creates the real master. SellingController.validate_items (`selling_controller.py:882`) checks Item.is_sales_item via `buying_controller.py:1327`. Check current native create/read rights and selected Company association; Item must be enabled, a sales Item, and have an appropriate Company default. Project.customer must match the selected Customer; the native controller permits blank Project.customer, but Cipher should create the real awarded Project with the actual customer explicitly.

A Lead issue requires an explicit already-existing Customer and a recorded reviewed Lead→Customer correspondence; never invoke the mapper's implicit Customer creation. Customer account/company association and native party/account visibility must be rechecked at effect time. Company, Customer, selected currency and native source rights remain current.

For `order_type=Sales` with `skip_delivery_note=0`, `validate_delivery_date` (`sales_order.py:425–445`) requires header/line delivery dates, propagates header dates to missing rows, and rejects dates earlier than transaction date. Set actual admitted delivery dates. Do not switch to Maintenance or enable skip-delivery solely to evade validation. `validate_proj_cust` at449–459 checks the Project customer. Stock items/product bundles require an appropriate native source warehouse unless legitimate supplier delivery applies (`sales_order.py:461–478`); drop ship requires a Supplier at514–517. The first bounded slice can admit non-stock sales items only and reject unsupported reservation, subcontracting, bundles, drop-ship and stock behavior explicitly. A generic quantity-one service Item must not silently replace an issued area/volume/length quantity: Item/UOM mapping must preserve its contractual dimension, quantity and price meaning. Any later consolidation requires an explicit approved allocation policy and exact source-line reconciliation.

## Exact units, price, taxes and reconciliation

Resolve qualified immutable UOM identity/revision and current native UOM rights. Pin native UOM, stock UOM, exact quantity string and exact rational conversion; use conversion factor1 when issued quantity is already in stock UOM, otherwise require an explicit supported conversion. Native `validate_uom_is_integer` checks both stock quantity and entered quantity (`sales_order.py:265–266`). Do not infer a new unit or change issued quantity to satisfy native precision.

For the current no-FX/no-tax commercial policy, require issued Currency == Company base currency == selling Price List currency; set conversion_rate and plc_conversion_rate1. Bind the current Company/currency/Price List versions and qualified currency exponent. Copy issued selected quantities/rates/amounts exactly; retain declared alternates outside the native order unless explicitly selected in the approved award manifest. Do not copy whichever alternates happen to be selected in a newer working Quotation.

Use normal native missing-value/tax/total validation. Disable unsupported pricing rules by the supported document flag, provide explicit zero discounts and no tax/shipping templates for this bounded policy, and reconcile after native validation. AccountsController.validate (`accounts_controller.py:292–337`) runs quantity checks, missing defaults, price-list validation, party-account and fiscal-date validation and native tax configuration; SellingController.validate (`selling_controller.py:51–68`) runs Item checks and pricing/stock-UOM conversion. Configured native defaults may change the result. Read persisted SQL DECIMAL columns as strings for each quantity, conversion, rate, amount, total, base total, discount and tax; compare using Decimal to the approved exact policy. Reject any unrepresentable value or inferred tax/FX/discount rather than rounding a contractual amount or claiming zero tax with nonzero native totals. A later tax-capable award needs an explicit independently bound tax policy, native accounts and reconciled tax rows.

## Registered writer and FIN admission integration

Sales Order is currently in the closed 12-type writer catalog at all before_insert/before_validate/validate/before_save/before_submit/before_cancel/before_update_after_submit/on_trash hooks. **Keep it closed now.** Future implementation requires one literal independently approved award action, exact server-owned effect context for that Issue/award/Company/new Project/order, current native create permissions, same-person global operation namespace, and atomic effect + native order + real Project + sidecar + receipt/history. Generic trusted_write is insufficient. A draft creation exception must not authorize edit/submit/cancel/delete, another order, or a mapper call. Submission is a separate explicitly qualified transition: native on_submit performs credit/authorization checks, reservations, Project sales updates, quotation status updates and other effects (`sales_order.py:519–540`). Sales Orders do not themselves post GL, but these operational obligations remain material.

FIN owner refinement: its Sales Order admission scan covers Company+Customer across all Projects, so the target Project row alone is insufficient. Existing FIN lock_sources already locks that native Customer row. Every future supported award-order insert/update/submit/cancel must also hold the exact same native Customer row after UOM→Currency in the sorted native source union, in addition to the real Project aggregate, before current locking admission reads or order writes. Company-only ambiguous channels remain closed until their own shared serialization contract exists. No new Company-after-Project lock is introduced.

Lock current canonical participants/identities before the exact source Company and real awarded Project aggregates, then established UOM→Currency→sorted native Item/party sources; the domain must declare deterministic issue/award-record ordering and atomic origin adoption. Every supported native SO writer affecting FIN admission must take the same declared admission lock before its write. FIN-01 currently treats native Sales Order activity conservatively as unqualified. PRJ-02 must add an exact recognized award-order admission rule and define its baseline/floor semantics with FIN; simply enabling SO creation while leaving the zero-activity scan unchanged would block later baseline admission or invalidate the concurrency claim. Raw SQL/host administration remains outside the application guarantee.

Required future actual tests: immutable Issue adopted despite newer Quotation draft without changing/submitting that draft; explicit Customer/Item absence refuses before writes; current Company/source/native revocation; same-person alias replay; concurrent independent consumption; native Item/UOM/tax/default reconciliation failure rolls all local effects back; matching Project customer and exact provenance retained; generic native mapper/write/submit/cancel/delete remains denied; accepted Company originals and historical sources stay readable only with current rights. This audit does not qualify any of those runtime outcomes.
