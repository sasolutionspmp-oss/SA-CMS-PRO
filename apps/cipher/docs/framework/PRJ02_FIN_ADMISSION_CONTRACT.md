# PRJ-02 ↔ FIN admission contract — preparation only

This is a proposed implementation boundary based on the [native award audit](PRJ02_NATIVE_AWARD_CONTRACT.md). It enables no writer, recognition exception, award, or financial floor. An actual independently approved COM-02 Issue now has [HTTP qualification](evidence/r1/company-com02-issue-http.json); the reviewed award interfaces and remaining COM-02 local distribution contract must qualify before award activation. Current FIN admission and the closed native financial catalog remain unchanged.

## Current source boundary

`construction_finance/sources.py:admission` scans Company/counterparty Sales Order, Sales Invoice and Delivery Note rows for a Customer; supplier channels use Purchase Order/Invoice/Receipt. Payment Entry and Journal Entry add counterparty/project scans. Stock Entry, Expense Claim, Timesheet and Material Request add conservative project or Company scans. Future installed obligation/certification channels require explicit contract linkage. A native draft counts as activity. Public snapshots retain only opaque status/provider/watermark, not unrelated native document names.

`service.lock_sources` already holds the real Project plus sorted historical/current UOMs, Currency and the native Customer/Supplier row before locked admission SQL. All 12 native financial writers remain denied at insert/validate/save/submit/cancel/update-after-submit/delete hooks. Generic `trusted_write` supplies no exception. `core.preserve_accepted` retains accepted line identity, quantity, cap and basis while the FIN-03 floor reader is unqualified.

## Shared admission mutex

The target Project alone is insufficient: the Sales Order scan spans every Project for the selected Company/Customer. A new award on another Project for the same Customer must serialize against the same native Customer row already locked by FIN. Supplier-side writers will require the corresponding Supplier row when independently qualified.

The proposed award sequence is canonical participants/identities → source Company → create and lock the actual new Project → deterministic Issue/award/adoption records → complete sorted UOM union → Currency → sorted native source union, including the exact Customer admission mutex. Every relevant source is collected before native locks. Existing Project FIN commands keep Project → UOM → Currency → Customer. A future supported order insert must hold the Customer mutex **before inserting** its native row; later changes must use the same Project/source order. No Company lock may be acquired late from a Project command.

Company-source authorization from a Project command must fit that order: acquire any required Company aggregate lock before Project, or use an explicitly reviewed authority check under the already acquired participant locks. Do not introduce a nested `require_company(lock=True)` after Project/native locks. Exact Company/Project participant-adapter integration remains an implementation prerequisite.

Native Sales Order observation after acquiring the mutex uses current `FOR UPDATE` reads. Foreign immutable Handoff/plan/adoption/line/Issue/baseline/contract-origin/decision/Consumption/receipt bodies and the minimal real Project scope/customer use nonlocking exact reads, avoiding inversion against their earlier source/receipt locks. A read-only inspection path uses the same pure lineage predicate without acquiring native order locks and grants no consequential admission. An earlier ordinary read may have established a MariaDB repeatable-read snapshot; the pinned database can reject lock promotion with error1020 instead of returning the current row. That outcome must fail closed, roll back, and retry the original intent/UUID in a fresh transaction before classifying committed activity. Never infer absence from the old snapshot. A missing Sales Order row cannot be protected by locking that absent row alone. Company-only ambiguous channels remain closed until their future writer declares a compatible mutex; this proposal provides no general financial bypass.

## Canonical recognition record and predicate

Reuse the future immutable **Cipher Award Handoff** as the recognition record. FIN must not introduce a second award master. The selected internal helper is `construction_finance.award_admission.recognize_award_sales_order(*, company, customer, sales_order_id, own_contract_id=None)`. It returns typed recognized-own, recognized-other or unqualified standing plus an opaque watermark, never a caller-selected allow flag. This trusted internal classification requires the already-held exact canonical Customer mutex and current locking native-order reads; all foreign immutable lineage reads remain nonlocking. An older repeatable-read snapshot missing newly committed lineage fails closed and retries the original intent in a fresh transaction. It has no actor parameter or optional nonlocking mode and acquires no late Company, foreign Project or UOM locks. Own contract/source/native authorization is a separate mandatory caller boundary. Implementation awaits the final handoff schema.

All of the following must agree before classifying an order as a recognized award obligation:

1. A unique consumed independently authorized award binds exact canonical Issue ID/digest, Proposal Revision ID/digest and accepted-estimate baseline IDs/digests. Issue sources retain their original Company scope and immutable line IDs. The owning caller separately enforces its required Company and original source/native rights. Current Project duties govern adopted Project facts; internal foreign classification grants no Project or source access.
2. Handoff, real Project, construction contract and native Sales Order link bidirectionally. Original Company equals each destination Company; Project.customer equals the selected existing Customer. A Lead requires an independently bound existing-Customer correspondence, with no implicit master creation.
3. The native order remains the explicitly supported draft (`docstatus=0`), with exact saved reconciliation digest and actual selected-line adoption. Native `prevdoc_docname`/`quotation_item` stay empty; an editable or newer Quotation is neither submitted nor substituted for the immutable Issue.
4. Every selected source line has its stable proposal UUID, exact award-line identity and explicit existing enabled sales Item mapping in the selected Company. Native/qualified UOM identity and revision, dimension, quantity, rational conversion, Currency, rate, amount, zero-tax/FX/discount policy and persisted native DECIMAL strings reconcile. Freeform lines without an admitted Item mapping fail before effects.
5. No duplicate source adoption exists. Canonical-person/UUID replay protects retries, and Issue adoption is unique. Issue uniqueness alone is insufficient: a legitimate successor Proposal Revision produces a distinct Issue. The first whole-award/new-Project slice additionally reserves **one canonical full Award Handoff per Company + Pursuit/native Opportunity lineage**, with exact source-line adoption across revisions/Issues/Proposals. Distinct cover/recipient reissues cannot create another Project/budget for the same opportunity. A second full award, re-award/amendment, partial or split allocation requires a separately reviewed contract and is unavailable initially.
6. All other observed native activity is either proven to belong to another exact registered contract/award through its own verified lineage, or remains `activity_unqualified`. A matching number, supplied Link field, generic trust flag, native `owner`, or zero fulfillment percentage is not recognition. Unknown/imported/stale/wrong-scope orders continue blocking initial admission.

The future FIN contract stores a server-owned award-origin snapshot outside the caller's closed commercial definition: handoff/Issue/revision/baseline identities and digests, destination Project/contract/order, selected-line lineage and saved order digest. A new admission provider/version must describe **recognized award obligations** explicitly. It must not reuse `new_contract_without_supported_obligations` to hide a recognized order. Create-time proof is rechecked during baseline manifest preparation and grant consumption; current accepted predecessor and exact source watermark remain bound.

Every bounded native scan must reject overflow before applying recognized-order exemptions. With the current `LIMIT 201` sentinel for a 200-row bound, observing the sentinel fails closed; filtering those rows must not hide an unknown 202nd obligation or turn an incomplete scan into no activity.

Astra selected bounded **server-internal integrity classification** for a registered order on another Project observed by the Company/Customer scan. Under the shared Customer mutex and current reads, the complete immutable handoff/native predicate must verify; unknown or inconsistent lineage fails closed. This classification grants no foreign Project access, source use or certification authority. Public admission remains opaque, with no foreign document IDs, Project IDs or counts. Do not acquire a late `require_project(lock=True)` after Customer to classify that foreign obligation. The actor's own award, source and native rights remain mandatory. This policy selects a future boundary; it enables no recognition implementation.

## Initial Project authority is explicit

A newly created real Project has no Cipher Project Duty. Company duties never inherit. Root/Astra selected the bounded atomic initial-team option below; backend owns its eventual central governance integration. The award writer remains deferred until its other dependencies are qualified.

The selected first slice binds a bounded initial project-team/ability manifest to the independently reviewed award. It names canonical participant IDs and exact allowed Project abilities; duplicate aliases cannot expand the grant. All participant/identity locks precede Company/Project/native locks. An explicit current **Company delegator capability** and a bounded server policy must authorize each grant at preparation and consumption; current Company eligibility, recipient activity and delegator revocation are rechecked. `commercial.write` or `company.read` alone must not silently become permission-administration authority. There is no implicit creator administrator. Native Frappe master permissions are separately current and are not copied from Company roles. New Project, exact scoped duties and governance history commit atomically with the award or all roll back. Returned Project content/navigation is authorized against those actual committed duties.

Separate assignment was considered but is not the selected first slice. Any later policy adopting that alternative must keep the award/source receipt Company-scoped and show pending Project access truthfully. It must not fabricate a Project capability, use a placeholder Project, copy Company privileges in bulk, or expose native Project details before access exists. It would still need its own current delegator policy and immutable evidence.

The award command/receipt remains Company-scoped. It carries the destination Project reference and explicit assignment outcome; a full Project read model is obtained through current Project authorization. A later revocation must not be mistaken for inherited Company access. The team manifest binds the governing delegation-policy revision and contains no wildcard or role-name expansion; all proposed recipients and the delegator join the canonical participant lock set.

The exact server-owned award contract factory must support a requester who is absent from that reviewed Project team. It runs only inside the registered atomic award effect, with separately checked Company award/delegation and own source/native authority. It must not call public `contract.create`, require a fabricated requester Project duty or grant one implicitly. Adopted Project facts use current Project authority; opening their original Company sources still requires the original Company/native/source rights.

## Floor and financial meaning

A recognized Sales Order proves commercial origin and an operational obligation. Its value, draft state, unbilled percentage or undelivered quantity supplies no certified/billed floor. Do not construct a zero `FloorSnapshot`, infer a zero certificate, or enable accepted cap reductions/deletions/UOM/currency/basis changes from order standing. Initial award-origin baseline admission still requires no unsupported/native billing or certification activity. Unknown activity remains unqualified.

FIN-03 must separately provide a registered typed `FloorSnapshot` binding contract/accepted SOV revisions, exact line amounts/quantities/UOMs, provider/version/watermark and correction authority. Existing accepted cap preservation remains in force until that reader is qualified. Award does not imply legal execution, notice to proceed, certification, payable, invoice, stock movement, GL posting or transmission.
