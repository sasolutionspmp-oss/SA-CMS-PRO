## Reuse and authority boundary

ERPNext owns the operational Supplier, Purchase Order, Purchase Receipt, Purchase Invoice and child rows, payable Accounts, taxes, GL, Payment Ledger and outstanding balance. Cipher owns original supplier-evidence intake, duplicate-resolution policy/evidence, immutable match/variance and approved application snapshots, project/contract/SOV allocation, exact approval manifests, native saved-record linkage, command receipt/history and provider handoff state. A Cipher AP record must not become a parallel payable ledger.

ADR004 remains settled: ERPNext is the sole operational ledger; QuickBooks is the official books target. A locally submitted PI really posts operational accounting. An accepted native or local outbox result does not mean QuickBooks accepted a Bill, an official payment occurred, a supplier application was legally certified or a document was externally distributed. The BUY receipt accrual/valuation mapping and the later PI accrual-clearing mapping must be reconciled together so receipt plus invoice cannot become two official expenses.

Initial project AP scope requires the real awarded Project and its exact Company, current canonical actor, declared AP duties, native Supplier/source/document rights and qualified contract/commitment linkage. A null Project does not infer Company authority. General Company overhead/no-project AP is a separate explicitly declared Company scope if later released, not a placeholder Project. Native parent and row links supplied by a client are never accepted as authority: the adapter resolves exact submitted source rows and verifies `row.parent`, Supplier, Company, Project, Item, UOM and canonical commitment-line identity.

## Native bill fields and duplicate admission

Native required header fields include naming series, Supplier, posting date, items and payable `credit_to`; controller defaults supply more required financial context. Native `bill_no` and `bill_date` are optional Data/Date. PI Item requires item_name, qty, UOM, conversion factor, stock quantity, rate/amount and base rate/amount fields; `item_code` is optional in the schema. This differs from the native Sales Order contract. Native ability to author a description-only line does not automatically qualify arbitrary accounts, no-PO exceptions or AEC certification.

`validate_supplier_invoice` runs for non-return invoices only. It checks a nonempty bill_no only when Accounts Settings `check_supplier_invoice_uniqueness` is enabled. Its query matches Supplier + exact bill_no + `docstatus < 2` + posting dates within the fiscal year selected using the current Company. It has **no Company condition** in that SQL. It therefore can reject the same Supplier number in another Company over that date range. It does not normalize bill numbers, require an original number, compare attachment evidence, enforce a database unique key or itself provide a concurrent-safe reservation. Returns skip this method; cancelled originals are excluded.

Cipher needs its own current, concurrent-safe duplicate admission, with explicit Company/Supplier policy and original evidence. Preserve original bill text, invoice date, supplier identity, exact original Document Revision/hash and extraction provenance; never invent or prefix a supplier bill number merely to evade native rejection. Normalization, annual number reuse, repeated installments, missing invoice numbers, credits/corrections and external-source identity each need a declared policy and lineage. There is no guessed universal Company+Supplier+number key that silently resolves every business case. Ambiguous or missing identity may be retained at intake, but blocks automatic posting pending explicit resolution. Different aliases share the canonical-person operation namespace; different operation IDs do not permit the same admitted original bill to post twice.

The future admission mechanism must serialize candidate identity/resolution under its exact business key and Supplier/Project/native-source locks, and enforce uniqueness in the appropriate canonical mapping/sidecar. Both concurrent different-UUID requests and retries after a lost response need actual proof. This stronger admission is additional to native validation: it must not bypass the native fiscal-year guard when that guard rejects a case. Supported configuration changes require their own authorized setup/version; no per-request `ignore_*`, ad-hoc SQL or undocumented native override is acceptable.

## PO/PR matching and configured exceptions

Native PO→PI mapper requires a submitted PO and generates an unsaved draft. It carries native PO child IDs, calculates remaining quantity from **submitted** PI rows plus rows already mapped into the requested target, and sets payment schedule/default payable account. Unit-price PO rows receive special zero-quantity treatment. These are draft conveniences, not accepted reservations or a duplicate-proof posting authorization. Two drafts can be prepared from the same remaining native capacity. The governed consume boundary must recheck current totals and exact allocations.

The separate `make_purchase_invoice_from_portal` calls mapping with `ignore_permissions=True`, verifies Supplier Portal User membership, saves and explicitly commits outside tests. It is not the adapter entrypoint for an atomic Cipher command. Keep ordinary native/legacy RPC catalog restrictions; use supported controller/mapping code internally with explicit permission and source checks, without invoking the portal save/commit wrapper or spoofing source docstatus.

PR→PI requires a submitted PR, carries PR/PO row provenance and excludes quantities already invoiced/returned according to the native maps. Its default basis is accepted `qty`. If Buying Settings `bill_for_rejected_quantity_in_purchase_invoice` is enabled, it uses physical `received_qty` instead, so rejected material can become billable. For example, accepted8/rejected2/received10 has different native billable quantity under those two configurations. Neither received10 nor accepted8 is an installed-work certificate. The adapter must bind this setting and the exact accepted/rejected/returned inventory policy; the first profile should refuse a bill-for-rejected configuration unless that policy has separately qualified. Do not silently change the site setting.

PI source comparison checks PO/PR header Supplier/Company/currency and row Project/Item/UOM when those references are present. Duplicate PO child references can be allowed; PR child duplication is treated differently. Return comparisons exclude UOM/conversion factor. These checks do not replace explicit parent-child ownership and canonical commitment/SOV allocation. Source submission status is checked on PI submit. PO hold/close checks and posting-date-after-PO validation also apply; native mapper availability never authorizes writing against a closed or incompatible source.

Rate equality is conditional on Buying Settings `maintain_same_rate`, non-return/non-internal conditions and `maintain_same_rate_action`; a configured role can override Stop, and Warn merely warns. Multiple billing checks aggregate submitted invoice amounts plus the current candidate, permit item/global overbilling allowances and a precision allowance, and can be bypassed by `role_allowed_to_over_bill`. Zero-value reference rows produce warnings rather than a universal cap check. Receipt billing logic has its own rejected-quantity and role/configuration conditions. Thus native “saved/submitted” is not proof of a strict Cipher match.

Cipher match revisions must use exact decimal quantity/money strings and qualified UOM/rational conversion, compare original billed quantity/rate/net/tax/total against explicit committed and accepted receipt/application allocations, retain unresolved variances and bind any approved exception. A native allowance or Frappe role does not grant a Cipher variance approval. Do not mutate native PO/PR quantities or accounts to make a mismatch disappear. The first profile can use zero policy variance and refuse unsupported zero-value/unit-price/FX cases until their own proofs exist.

`po_required` applies according to Buying Settings and Supplier `allow_purchase_invoice_creation_without_purchase_order`. `pr_required` applies to stock/asset items when update_stock is off, with its own Supplier exception. Native service/non-stock no-receipt behavior is therefore different from stock no-receipt behavior. A reviewed Cipher no-PO/service exception still needs compatible supported native configuration; it cannot bypass a native required-PO rule. Intake and resolution may proceed while posting remains blocked for required setup. No dummy PO, receipt, Item or Project should be fabricated.

## Posting and accounting profile

PI `on_submit` updates withholding, verifies previous submitted documents, updates source billing statuses, enforces native Authorization Control, reconciles advances, may create Stock Ledger entries/repost valuation when update_stock is set, posts GL, may update native Project purchase cost/margin and may perform common-party accounting. Its GL includes Supplier payable, expense or receipt-accrual/asset/stock accounts, tax/valuation, withholding, precision loss, payment, write-off and rounding effects. Native currency and float precision must be reconciled to the approved exact decimal policy, not copied into wire floats.

The first bounded profile should explicitly require base currency, approved financial period/date, current valid payable/expense/tax/cost-center/dimension mappings, qualified project/contract allocations and a reviewed Company accounting configuration snapshot. It should exclude `is_paid`, paid_amount/cash-bank effects, `update_stock`, automatic advance allocation and populated advances, common-party reconciliation/Party Link effects, internal transfer/intercompany invoices, deferred expense, assets, unreviewed withholding/taxes, landed-cost revaluation and unqualified FX. Exclusions are admission rules, not silent edits to configured business settings. Native accounts/taxes that would differ from the approved profile make the operation unavailable until their own adapter/GL contract qualifies.

Stock inventory under perpetual accounting normally uses Stock Received But Not Billed, with special opening/drop-ship/fixed-asset branches. `set_expense_account` can change a candidate's account to the warehouse account or receipt-accrual account. An invoice before receipt can still debit the receipt-clearing account in relevant native cases. Non-stock provisional accounting has a separate receipt-accrual/expense path; setting invoice-based landed-cost adjustment can alter receipt valuation. These are real operational behaviors, not evidence of duplicate ledgers. The registered profile must bind and compare them. Initial PI posting from an already qualified receipt uses update_stock0, so the same physical goods are not received twice.

`is_paid` can create native cash/bank GL entries during PI submit without a separate payment command. Automatic advances can select existing entries and reconcile them; common-party accounting can create a Journal Entry. The initial profile must reject these inputs/configurations unless individually reviewed, posted and reconciled in an explicit later slice. An invoice payment hold is not a retainage calculation. Native block/unblock/release-date methods use direct db_set with native write permission after submission; future governed payment-hold controls must close those generic routes and authorize an exact action rather than relying only on validate hooks.

FIN-04 must submit through the standard controller inside the exact independently granted effect context. Compare the saved native PI fields/children against the reviewed draft digest and compare the **actual** newly generated voucher GL/Payment Ledger/stock footprint against the manifest's expected account/currency/debit-credit/party/Project/dimension totals. Native taxes, rounding, budget/cost-center allocation, period rules and Project cost updates are included in that comparison. Any mismatch rolls back the PI, ledger, consumed grant, history, command receipt and official-delivery intent together. No provider call occurs inside that transaction.

The existing closed financial writer catalog remains in force. Future enablement must be an exact per-action, per-voucher, per-version server context for supported draft/submit/cancel/correction paths. No generic trusted-write exception or blanket native-doctype allowance qualifies posting. Supplier row/current source locks also serialize the FIN admission scan across different Projects using the same Supplier; the target Project alone is insufficient. Preserve established Person→identity→aggregate→sorted UOM→Currency→sorted native Item/party ordering and declare domain record ordering.

## AEC applications, installed work and retainage

Native PI matching is commercial/accounting evidence. It does not certify installed work, approve a subcontract pay application, authorize SOV overrun, consume previously billed stored materials or release retainage. FIN-03 needs immutable prior/current/cumulative installed-work certificates, application revisions, approved contract/SOV/policy references, stable line identities and exact authority. A supplier's proposed cumulative quantity must not overwrite previously accepted actuals. A site physical receipt is not installed quantity; rejected material and title/insurance/storage eligibility need their own policy.

Stored material billed before installation must be tracked as its own approved lot/allocation and consumed or transferred as work is installed, so the supplier cannot bill the same value again as installed work. Match and posting manifests bind the exact previous accepted state and the current signed application/certificate; concurrent applications cannot independently consume the same remaining SOV/lot allowance. Corrections append linked reversal/successor events rather than reducing accepted history in place.

Native tax withholding/TDS is not contractual retainage. FIN-05 must define gross certified value, retainage withheld, prior/current/cumulative release and the operational/official payable-account treatment. Do not lower the original line rate or hide a 10% holdback in a tax row merely to make net payment90 from gross100. If retainage is nonzero and its ledger contract is not yet qualified, initial posting stays blocked while intake/review evidence remains available. Accepted FIN-01 baselines/caps are not themselves evidence that FIN-03 floors or FIN-05 release mechanics have executed.

## Returns, cancellation and amendment

Native `make_debit_note` delegates to the standard return mapper. It requires a submitted source, sets is_return/return_against, negates supported line/tax values, preserves source linkage, clears copied advances and disables automatic advance allocation. Return validation with an explicit original compares party/account, quantities already returned and relevant UOM/stock quantities; a non-stock/no-update-stock invoice has different warehouse requirements from a stock return. Native standalone returns are possible in some paths without the same original-linked checks, so the first governed correction profile must require exact original voucher/row lineage and current approval rather than infer a valid credit from negative amounts.

PI cancel updates billing status, reverses GL/payment ledger, may reverse stock/repost valuation, update native Project cost and unlink/interact with payment/intercompany references depending on settings. Frappe amendment requires docstatus2 and can copy attachments from the cancelled original. These are not harmless edits to an approved bill. Allow-on-submit account/cost-center changes can trigger reposting and also need explicit action control. A changed native supplier invoice, accepted application or official-book acknowledgment requires a linked correction case with exact current financial state, not reuse of an old grant or a rewritten original PDF.

QuickBooks acknowledgment changes the correction dependency: a native cancellation is not proof that an official QBO Bill was voided or credited. Preserve official external IDs/versions and original delivery keys. INT-02 must qualify the provider's actual correction/void/credit capability and readback for the specific state; do not issue an unsupported second expense or assume an ambiguous original handoff failed. Native payment, official payment and retainage-release authority remain separate commands.
